# Workbench features against the workspace seams

Research for pmelab/gtd#590 (map pmelab/gtd#589).

**Source:** pmelab/workbench at `39effe5` (2026-11-13), read in
`~/Workbench/workbench/main`. Every `file:line` below is in that tree. Nothing
was run.

**Buckets** (the decisions come from the map's Notes):

| Code          | Meaning                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| **CORE**      | gtd workspace command (supervisor, inbox and dispatch, one server for the dashboard and the gate pages) |
| **A:term**    | adapter default: terminal = rex                                                                         |
| **A:svc**     | adapter default: services = pitchfork                                                                   |
| **A:wt**      | adapter default: worktrees = worktrunk                                                                  |
| **A:act**     | adapter default: actions = mise                                                                         |
| **A:ntfy**    | adapter default: notifications = ntfy                                                                   |
| **U:driver**  | workbench userland: the driver (`bench:work`)                                                           |
| **U:trigger** | workbench userland: a TypeScript trigger (files items, reacts to lifecycle events)                      |
| **U:action**  | workbench userland: an action task (`start:*`, `gate:*`, `error:*`, `any:*`)                            |
| **U:machine** | workbench userland: machine setup (`bench:infra`, wt.toml, wrappers)                                    |
| **DROP**      | dropped or out of scope (see the map's "Out of scope")                                                  |

Each feature has exactly one bucket. When a feature also needs something from a
second seam, the "Notes" column says so. Features marked **⚑** fit no bucket
cleanly. The section [Fits no bucket](#fits-no-bucket) lists them.

State shorthand: `S/` = `$BENCH/.state/`, `GD/` = the checkout's git dir
(`git rev-parse --absolute-git-dir`), `wt vars` = worktrunk marker and vars on
the branch.

## Fits no bucket

These features cross a seam the map's decisions do not yet cover. Each line
names the gap.

1. **Userland lifecycle events into gtd (1.3, 7.23–7.26, 9.4).** `ship:*`,
   `deploy:*`, `poll:*`, `merged` and `checks red` come from userland (ship.sh,
   triggers) and change the row's status and the pushes. OSC 7501 covers only
   the driver's own pane. gtd needs an input channel for userland events, or
   these errors stop showing on the dashboard. This is the map's open "lifecycle
   events from outside".
2. **Automatic reactions to worktree status (7.27 auto-triage, 7.28 red-baseline
   autofix, 5.7 REDRIVE).** Today these run an action, or Proceed, when a _row_
   turns ❌ or reaches a known gate label. The map's triggers react to _item_
   lifecycle events, and actions run only on a click. A trigger event "worktree
   status changed", and a way for a trigger or action to ask for Proceed or
   Retry, would cover them. Dropping them is the other option.
3. **PR feedback gate (7.22).** A trigger writes `.gtd/REVIEW.md`, and the core
   shows a synthetic 🙋 with no gtd gate behind it. Proceed then runs
   `start fix` instead of moving a driver. Possible model: the trigger files an
   item that targets an existing worktree (start action `fix`). The "gate" is
   then a `proposed` item that waits for the person to accept it. The inbox
   needs "item for an existing worktree" and "accept a proposed item".
4. **Re-processing a started item in place (7.21).** A re-requested review
   hard-resets an existing worktree and restarts it. Same inbox gap as 3.
5. **Crash restart of the driver (4.9).** The detection reads the driver's
   private `driver.json` and lock. The driver contract must give gtd a signal it
   can read itself.
6. **Error kinds that pick the row actions (5.9).** Buttons depend on the error
   kind (`drive`, `ship`, `conflict`), not on the status alone. The `error:*`
   prefix gives only the status. The contract needs the error kind (or the last
   record's `kind`) as an action filter, or every `error:*` action shows on
   every ❌ row.
7. **Driver needs the item's ship mode (6.9, 10.1).** The driver reads the queue
   to decide whether to ship. Once gtd owns the inbox, gtd must pass this fact
   on the driver invocation.
8. **Dispatch-time policy re-check (7.9).** The lean-on-public-repo refusal also
   blocks items that were filed earlier. Triggers only file items, so a "may
   start" hook is missing.
9. **Project deploy guarded by core facts (7.26).** The deploy must wait for the
   dispatch lock and for "no driver of this project runs". A trigger cannot see
   either fact unless the trigger API exposes them.
10. **Items no trigger filed (7.25).** A hand-started lean PR gets an inbox item
    after the fact so that its merge is watched.
11. **The judge file (1.8).** The dashboard imports the driver's `JUDGE_FILES`.
    gtd should report the file a judge reads in `gtd next`.
12. **Housekeeping placement (4.8, 4.9, 8.8).** These are placed in CORE here as
    a proposal. The map lists them as undecided.

## External CLI calls by seam (for the adapter contracts)

- **Terminal (rex):** `session ls|rename`, `new`, `window ls|new|close|focus`,
  `block ls|send`, `block call … process|program_status`, `events -s … --json`;
  plus `ps -o ppid=` for the login-shell case.
- **Services (pitchfork):** `config add|remove` (namespace, label, dir),
  `start --local`, `stop`, `restart`, `list --json`, `daemons --json`,
  `proxy status --json`, `proxy add|remove`, `settings get|set`. It also edits
  `~/.config/pitchfork/config.toml` directly.
- **Worktrees (worktrunk):** `list --format=json` (branch, path, `display.state`
  integrated, changes, marker, vars), `switch -c <b> -y --no-cd --base <ref>`,
  `switch pr:<n>`, `remove -y [-f -D] <b>`, `config state marker set`,
  `config state vars set|clear`; the hooks `post-start` and `pre-remove`
  (`wt.toml`).
- **Actions (mise):** `tasks ls --json`, `tasks info <t> --json`
  (`usage_spec.cmd`), `run [-q] <task> [flags] [-- args]`, `trust -yq`,
  `env -s bash`, `x --`.
- **Notifications (ntfy):** HTTP POST only.
- **Not behind any adapter today:** `gh` (sources, transitions, PR watch, ship),
  `acli` (Jira), `claude` (driver, triage, resolve, commit messages), `git`
  (everywhere), `gtd`, `tailscale`. All of them stay userland except `git` and
  `gtd`, which gtd uses in-process.
